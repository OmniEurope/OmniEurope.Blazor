# Dépendances et chaîne d'outillage

Les versions directes sont centralisées dans `Directory.Packages.props`; les résolutions transitives sont figées dans les fichiers `packages.lock.json`. Le fichier `eng/dependency-policy.json` conserve la date et la source de la revue manuelle des versions sensibles. Les mises à jour du SDK .NET et des paquets NuGet se font à la main : aucune proposition automatique.

## Décisions vérifiées le 26 octobre 2026

- les packages ASP.NET Core et `Microsoft.Extensions.Localization` sont en `10.0.14` et `bunit` en `2.13.3`, dernières versions stables publiées par NuGet.org.
- la bibliothèque a trois dépendances d'exécution, déclarées dans `src/OmniEurope.Blazor/OmniEurope.Blazor.csproj` : `Microsoft.AspNetCore.Components.Web`, `Microsoft.Extensions.Localization` et `HtmlSanitizer` (`9.2.1039`, dernière version stable au relevé de `eng/dependency-policy.json`), qui assainit le HTML d'`OmniHtmlEditor` par liste blanche et apporte AngleSharp en transitif.
- la chaîne de tests tourne sur Microsoft.Testing.Platform, déclaré par le bloc `test` de `global.json`. `xunit.v3` `4.0.2` embarque son propre exécuteur, donc ni `Microsoft.NET.Test.Sdk` ni `xunit.runner.visualstudio` ne sont nécessaires. `coverlet.MTP` `10.1.0` produit le Cobertura (`--coverlet --coverlet-output-format cobertura`, restreint à `[OmniEurope.Blazor]*`) et `Microsoft.Testing.Extensions.TrxReport` `2.5.1` le TRX (`--report-trx`).
- les packages MAUI restent sur `10.0.101` : en `10.0.120`, le code XAML que MAUI génère pour l'hôte Windows (`XamlTypeInfo.g.cs`) appelle `MauiWinUIApplication.Services` et `.Application`, devenus obsolètes, et le build Release, qui traite les avertissements en erreurs, échoue (`CS0618`, relevé le 26 octobre 2026);
- `Microsoft.CodeAnalysis.CSharp` est en `5.0.0`, le compilateur du premier SDK .NET 10 (`10.0.100`). Un analyseur ne peut pas référencer un compilateur plus récent que celui du SDK qui le charge (`CS9057`), et un projet qui référence ce dépôt par `ProjectReference` charge les analyseurs avec son propre SDK : en visant le plus ancien compilateur .NET 10, tout SDK `10.0` les charge. Vérifié le 2026-09-18 sous `10.0.202`, `10.0.303` et `10.0.401` ; avec `5.9.0`, `10.0.202` échoue en `CS9057`. Un test de convention fige cette version.
- le SDK a un plancher unique dans `global.json` (`version: 10.0.100`, `rollForward: latestFeature`) : toute bande `10.0` à partir de `10.0.100` convient (ADR-002). Aucun workload set n'est figé : seul le job MAUI installe `maui-windows`, et `eng/Test-SdkBand.ps1` vérifie le plancher dans les deux jobs plutôt que de recopier un numéro dans les workflows. Les hôtes WebAssembly reçoivent du SDK trois paquets implicites à la version de son runtime (`Microsoft.NET.ILLink.Tasks`, `Microsoft.NET.Sdk.WebAssembly.Pack`, `Microsoft.AspNetCore.App.Internal.Assets`) ; `Directory.Build.targets` les épingle sur `OmniImplicitSdkPackVersion`, alignée sur les paquets `Microsoft.AspNetCore.*`, pour que les verrous se restaurent en `--locked-mode` sous toute bande (sans ce pin, `NU1004` sous `10.0.202` et `10.0.303`). La restauration verrouillée se fait en Release : en Debug, un SDK `10.0.1xx` ou `10.0.2xx` injecte aussi `Microsoft.DotNet.HotReload.WebAssembly.Browser` à sa propre version, impossible à épingler. Le pack d'exécution Mono des hôtes WebAssembly (`Microsoft.NETCore.App.Runtime.Mono.browser-wasm`, d'où viennent les bibliothèques natives de `dotnet.native.wasm`) suit la même version : un workload `wasm-tools` installé le ramènerait au runtime qu'il embarque (`10.0.13` sous le manifeste `10.0.113`), sans le correctif Brotli de `10.0.14` (GHSA-p3jp-9v83-76w9) ; la cible `OmniPinMonoRuntimePack` le remet sur `OmniImplicitSdkPackVersion` (le pack manquant se restaure depuis NuGet, il n'entre pas dans les verrous) et `eng/Test-WasmRuntimeVersion.ps1 -PublishPath <dossier>` échoue quand un `dotnet.native.wasm` publié porte une autre version.

## Application vitrine

La vitrine (`site/`) est une application déployée qui ne fait pas partie du paquet NuGet : ses projets ne sont pas empaquetables et ses dépendances n'entrent pas dans celles de la bibliothèque. Relevé du 27 octobre 2026, dernières versions stables publiées par NuGet.org :

- l'API `OmniEurope.Blazor.Showcase.Back` utilise `Npgsql.EntityFrameworkCore.PostgreSQL` `10.0.3` (PostgreSQL est le seul fournisseur), `Microsoft.Extensions.Diagnostics.HealthChecks.EntityFrameworkCore` `10.0.14` pour `/health/ready` et `Microsoft.EntityFrameworkCore.Design` `10.0.14`, réservé à la génération des migrations (`PrivateAssets=all`, absent de la publication);
- `tests/OmniEurope.Blazor.Showcase.Back.Tests` utilise `Microsoft.AspNetCore.Mvc.Testing` `10.0.14` et `Testcontainers.PostgreSql` `4.16.0`, qui démarre un vrai PostgreSQL `postgres:18-alpine` dans Docker;
- la base de développement locale est l'image `postgres:18-alpine` de `deploy/compose/dev-db.compose.yml`.
## Ressources tierces hors NuGet

Les ressources recopiées dans le dépôt sont déclarées dans `eng/vendored-assets.json`, qui pilote leur section dans `NOTICE.md`, leur composant CycloneDX et la conservation de leur texte de licence. Y figurent aujourd'hui cinq ressources : Phosphor Icons `2.1.1` (MIT), source des tracés intégrés d'`OmniIcon`, et les quatre polices web variables du catalogue `OmniThemeFonts` servies par le paquet (sous-ensemble latin, Fontsource `5.3.0`, OFL-1.1) : Inter, Lexend, Source Serif 4 et JetBrains Mono. Toute mise à jour doit rejouer `eng/Generate-Sbom.ps1` puis `eng/Test-Sbom.ps1`.

Toute modification doit mettre à jour les verrous, passer les tests et conserver les contrôles de couverture, de SBOM et de licences.
